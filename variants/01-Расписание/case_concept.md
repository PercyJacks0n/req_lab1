## 6. Границы кейса

### 6.1. In Scope

- FE-1. Автоматический импорт готового расписания в формате JSON из корпоративной системы 1С:Университет ПРОФ.   
- FE-2. Оптимизация, очистка от дублирующихся записей разных служб и надежное хранение расписания во внутренней базе данных микросервиса Чат-бота MAX.
- FE-3. Выдача актуального расписания студентам и преподавателям по командам внутри мессенджера через Чат-бот MAX (MAX Bot).   
- FE-4. Автоматическая рассылка уведомлений пользователям в Чат-боте MAX при изменении расписания (отмены, переносы, смена аудитории или преподавателя).   
- FE-5. Разработка отдельного веб-сервиса Мини-приложения (MAX Mini App), который открывается внутри мессенджера MAX (через WebView) и доступен в веб-браузере, получая данные о расписании по API от микросервиса Чат-бота.
- FE-6. Формирование сводной аналитики и отчетов по загрузке аудиторий и преподавателей на основе хранимого расписания.

### 6.2. Out of Scope

- LI-1. Разработка автоматизированного рабочего места (АРМ) диспетчера и сеточного конструктора для ручного составления расписания (система импортирует уже сформированное расписание из внешних систем вуза).   
- LI-2. Первичный учет, ввод и редактирование справочников кадрового состава, контингента студентов, аудиторного фонда и учебных планов (ведутся во внешних системах вуза).   
- LI-3. Разработка нативных мобильных приложений под ОС iOS и Android для магазинов App Store и Google Play (клиентский доступ обеспечивается через Чат-бот MAX и веб-сервис Mini App).   
- LI-4. Учет посещаемости занятий, ведение электронных журналов успеваемости и выставление оценок.   
- LI-5. Автоматическая генерация сетки расписания с использованием алгоритмов искусственного интеллекта и нейросетей.

### 7.4. Особенности развертывания

Серверная часть приложения развертывается во внутреннем контуре университета на серверах под управлением Linux в изолированных Docker-контейнерах. Для работы интеграционного шлюза с платформой MAX необходимо настроить исходящее HTTPS-соединение через межсетевой экран вуза к шлюзу MAX Bridge API и применить сервисный Bearer-токен, полученный от digital.vuz@max.ru.   Все действия в системе защищены ролевой авторизацией: при входе диспетчера через единую учетную запись и при каждой публикации расписания в базу данных и журнал безопасности записывается уникальный идентификатор, ФИО и роль сотрудника, авторизовавшего операцию. Для диспетчеров учебного управления подготавливаются видеоинструкции (до 5 минут) и интерактивный тур по интерфейсу, обучающие запуску парсинга, разрешению конфликтов по правилу BR-2, проверке статуса публикации в MAX Mini App и отправке уведомлений через MAX Chat Bot.

## 8. Риски

| ID | Риск | Вероятность (0–1) | Ущерб (1–10) | Митигация |
|----|------|-------------------|--------------|-----------|
| RI-1 | Низкое качество исходных данных в 1С или обрыв выгрузки, грозящие поломкой существующей сетки расписания | 0,7 | 8 | Реализовать принцип «Гарантия: слома нет»: строгий шлюз предвалидации при парсинге, атомарные транзакции с полным откатом (Rollback) при ошибке и запрет физического удаления записей (soft delete), уже задействованных в сетке. |
| RI-2 | Изменения в контракте или временная недоступность шлюза MAX Bridge API | 0,3 | 8 | Вынести интеграцию с MAX Bridge API в изолированный модуль-адаптер; предусмотреть локальное сохранение версий расписания, очередь повторной отправки (retry) и резервный экспорт в .xlsx по шаблону MAX. |
| RI-3 | Превышение лимитов пропускной способности (Rate Limiting) шлюза MAX Bridge API при пакетной публикации | 0,5 | 6 | Реализовать пакетную отправку через асинхронную очередь с батчингом (дроблением на порции по 100–300 записей) и управляемыми задержками между запросами. |
| RI-4 | Несанкционированное изменение расписания или невозможность установить автора некорректной правки | 0,4 | 7 | Внедрить строгую ролевую авторизацию и неизменяемый журнал аудита (Audit Log), фиксирующий ФИО, ID сессии и точное время для каждого изменения ячейки или запуска публикации в MAX. |
| RI-5 | Рассинхронизация данных между MAX Mini App и MAX Chat Bot при лавинообразных правках в первую неделю семестра | 0,8 | 4 | Оптимизировать транзакции точечных обновлений; реализовать единую шину событий через MAX Bridge API и буферизацию (debounce) уведомлений перед отправкой в чат-бот. |
| RI-6 | Сопротивление диспетчеров: нежелание переходить с таблиц Excel на новый веб-интерфейс | 0,5 | 5 | Проектировать интерфейс по привычной ментальной модели сетки Excel с поддержкой горячих клавиш; провести очное обучение диспетчеров. |

> [!WARNING]
> Наибольший совокупный ущерб связан с качеством исходных данных (риск RI-1). Поскольку ключевой принцип заказчика исключает ручной ввод справочников, работоспособность конструктора напрямую зависит от валидности данных, переданных ИТ-отделом. Модуль импорта должен сразу отсекать некорректные записи с генерацией диагностического журнала.

## 9. Критерии приемки

| ID | Критерий | Как проверяется | Порог | Срок |
|----|----------|-----------------|-------|------|
| SM-1 | Сокращение срока парсинга, формирования и публикации чистового расписания на семестр | Хронометраж процесса учебного управления от старта парсинга нагрузки из 1С до публикации в MAX | Не более 7 рабочих дней | Приемка выпуска 1 |
| SM-2 | Полное исключение дублирующего ручного ввода справочных данных за счет автопарсинга | Аудит журнала создания сущностей в базе данных приложения | 100% справочников получены парсингом из 1С (0 сущностей, введенных вручную) | Приемка выпуска 1 |
| SM-3 | Отсутствие накладок в опубликованном расписании | Анализ сетки и проверка отчетов об инцидентах за первую учебную неделю | 0 накладок аудиторий, преподавателей и учебных групп | 1-я неделя семестра |
| SM-4 | Раздельный охват аудитории через MAX Mini App и MAX Chat Bot | Аналитика открытий мини-приложения и статистика активных подписчиков чат-бота вуза | Не менее 75% студентов и 60% преподавателей в Mini App; ≥90% успешной доставки уведомлений в Chat Bot | 1 месяц после релиза |
| SM-5 | Время формирования аналитического отчета по загрузке аудиторий и преподавателей | Замер времени генерации отчета в веб-интерфейсе | Менее 5 секунд на построение любого сводного отчета | Приемка выпуска 1 |
| AC-1 | Реализация функционального объема выпуска 1 (MVP) | Чек-лист проверки FE-1, FE-2, FE-3, FE-4, FE-5 | 100% запланированных сценариев выпуска 1 | Приемка выпуска 1 |
| AC-2 | Корректность интеграции через MAX Bridge API для обоих каналов (Mini App и Chat Bot) | Тестовая передача массивов расписания и триггеров уведомлений через шлюз MAX Bridge API | Код ответа HTTP 200/201 от MAX Bridge API; корректное отображение сетки в Mini App и доставка сообщения в Chat Bot | Приемка выпуска 1 |
| AC-3 | Гарантия целостности данных при сбоях парсинга и внешних систем | Нагрузочное и негативное тестирование: подача поврежденного JSON из 1С и принудительный обрыв связи с MAX Bridge API | 100% сохранение действующего расписания без потери пар | Приемка выпуска 1 |

Учебное управление принимает систему Выпуска 1, если в полном объеме выполнены критерии AC-1, AC-2, AC-3 и AC-4, подтверждающие работоспособность потокового парсинга, прозрачную фиксацию автора каждого действия, блокировку пересечений и бесшовную интеграцию через MAX Bridge API как для мини-приложения, так и для чат-бота. Метрики эффективности SM-1...SM-5 служат целевыми показателями (KPI) ввода системы в постоянную эксплуатацию и оцениваются по итогам первого семестрового цикла и реальной активности пользователей в экосистеме MAX.
