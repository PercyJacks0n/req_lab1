
## 3. Эпики

### EP-1. Автоматически импортировать и оптимизировать расписание из 1С

- Уровень: эпик
- Узел дерева: Автоматический импорт JSON из 1С / Хранение расписания в собственной БД
- Бизнес-цель: BO-1 (Исключение ручного ввода и дублирования данных)
- Источник: Учебное управление (Заказчик), ИТ-отдел университета
- Приоритет: Must

**Пользовательская история.** Как сотрудник Учебного управления, я хочу, чтобы система автоматически забирала готовый JSON с расписанием и справочниками из «1С:Университет ПРОФ» по защищенному каналу, очищала данные от дубликатов и сохраняла их в локальной базе микросервиса, чтобы полностью исключить ручной ввод и обеспечить доступность расписания пользователям даже при сбоях в 1С.

**Сценарий UC-1.**

| Поле | Содержание |
| ----- | ----- |
| Акторы | Подсистема Коннектор (Микросервис). ИТ-система «1С:Университет ПРОФ». Сотрудник Учебного управления |
| Предусловия | В настройках Коннектора заданы адреса сервисов 1С и параметры доступа |
| Триггер | Наступление времени автоматической синхронизации по расписанию или ручной запуск администратором |
| Постусловие успеха | В базе микросервиса сохранено актуальное расписание без дублей и справочники; результат записан в лог |
| Постусловие отказа | Новые данные в базу не записаны; микросервис продолжает использовать предыдущую рабочую копию |

Основной поток:

1. Подсистема Коннектор отправляет служебные HTTP GET-запросы по защищенному каналу к сервисам 1С.
2. Сервер 1С возвращает сформированный массив данных в формате JSON по защищенному каналу связи.
3. Коннектор принимает файл во временное хранилище и обрабатывает данные в памяти, отсекая служебный префикс до первого символа `{` или `[`.
4. Коннектор очищает записи от дубликатов, поступивших от разных подразделений вуза.
5. Коннектор обновляет внутреннюю базу данных микросервиса и сохраняет результат импорта.

Альтернативы:

1. Точечный импорт: для получения деталей учебных планов и дисциплин кафедр (`disciplines_departments`) Коннектор запрашивает данные отдельными GET-запросами по каждому номеру учебного плана (`plan_number`).

Исключения:

1. Превышение таймаута ответа 1С. Коннектор обрывает сеанс, записывает таймаут в журнал ошибок и сохраняет в базе данных предыдущую рабочую версию.
2. Сервер 1С вернул ответ с признаком `"error": true` или поврежденный JSON. Коннектор отбрасывает поврежденный пакет без изменения локальной базы и выводит администратору системы сообщение об ошибке.

### EP-2. Вести журнал аудита системных действий и публикаций

- Уровень: эпик
- Узел дерева: Аудит и логирование / Логирование факта публикации
- Бизнес-цель: BO-1 (Прозрачный аудит и контроль системных операций)
- Источник: Учебное управление (Заказчик)
- Приоритет: Must

**Пользовательская история.** Как сотрудник Учебного управления, я хочу, чтобы система фиксировала в журнале аудита все ключевые события (сеансы автоматического импорта, выгрузку данных в MAX Bridge API, формирование резервных копий) со временем и статусом, чтобы обеспечить прозрачный контроль за движением данных расписания.

**Сценарий UC-2.**

| Поле | Содержание |
| ----- | ----- |
| Акторы | Сотрудник Учебного управления. Администратор системы. Микросервис расписания |
| Предусловия | Пользователь авторизован в системе под своей учетной записью (или действует таймер фоновых заданий) |
| Триггер | Выполнение ключевой операции (старт импорта, отправка в MAX Bridge API, выгрузка Excel, ошибка синхронизации) |
| Постусловие успеха | В таблицу аудита добавлена новая запись с параметрами операции |
| Постусловие отказа | Операция прерывается с фиксацией ошибки безопасности, если запись аудита не может быть сохранена |

Основной поток:

1. Система (или администратор) запускает операцию (например, фоновую синхронизацию с 1С или пакетную отправку в MAX Bridge API).
2. Микросервис фиксирует событие и проверяет, кто запустил операцию (логин администратора или автозапуск).
3. Микросервис формирует запись журнала аудита: время, инициатор (ФИО ответственного или системный код `System.Connector`), тип действия, какие подразделения затронуты и статус выполнения (`Success` / `Failed`).
4. Запись сохраняется в базу данных аудита.
5. При обращении сотрудника Учебного управления система показывает журнал аудита с фильтрами по датам, операциям и статусам.

Альтернативы:

1. Фоновое регламентное задание: при автоматической синхронизации по таймеру в поле инициатора вносится системный идентификатор `CRON_DAEMON`.

Исключения:

1. Сбой записи в таблицу журнала аудита. Система останавливает операцию и отправляет оповещение администратору безопасности.

### EP-3. Контролировать накладки и коллизии аудиторного фонда (правило BR-2)

- Уровень: эпик
- Узел дерева: Контроль конфликтов и накладок / Дедупликация и оптимизация данных
- Бизнес-цель: BO-1, BO-3 (Предотвращение накладок и срывов учебного процесса)
- Источник: Учебное управление (Заказчик)
- Приоритет: Must

**Пользовательская история.** Как сотрудник Учебного управления, я хочу, чтобы система автоматически проверяла импортированное расписание на одновременную занятость преподавателей (правило BR-1) и пересечения групп в одной аудитории (правило BR-2), чтобы вовремя находить несогласованность данных от разных кафедр вуза.

**Сценарий UC-3.**

| Поле | Содержание |
| ----- | ----- |
| Акторы | Подсистема Коннектор (Микросервис). Сотрудник Учебного управления |
| Предусловия | В оперативную память микросервиса поступил новый пакет расписания из 1С |
| Триггер | Завершение первичной очистки данных от дубликатов в процессе импорта |
| Постусловие успеха | Все пары сетки проверены; найденные накладки помечены как «Конфликт» с указанием причин и сохранены для отчета |
| Постусловие отказа | Процесс проверки прерван из-за нарушения структуры данных; администратор уведомлен об ошибке |

Основной поток:

1. Микросервис запускает проверку полученной сетки занятий на пересечения.
2. Система проверяет правило BR-1: отсутствие у одного преподавателя двух и более назначенных занятий в одно время.
3. Система проверяет правило BR-2: в одной физической аудитории в один временной интервал может находиться только одна учебная группа.
4. При совпадении аудитории и времени система проверяет наличие признака объединения групп в потоковую лекцию.
5. Если признак потоковой лекции отсутствует, система регистрирует нарушение правила BR-2, помечает занятие как конфликт и сохраняет параметры накладки (аудитория, день, время, конфликтующие группы).

Альтернативы:

1. Потоковое занятие: система проверяет, что группы объединены на одну общую дисциплину к одному преподавателю, а вместимость аудитории достаточна; конфликт BR-2 не фиксируется.

Исключения:

1. В записи расписания отсутствует номер физической аудитории («дистанционное занятие» или «консультация»). Система пропускает проверку физического помещения (BR-2) и выполняет только проверку занятости преподавателя (BR-1).

### EP-4. Формировать аналитические отчёты по загрузке аудиторий и преподавателей

- Уровень: эпик
- Узел дерева: Отчёты по загрузке аудиторий и штата
- Бизнес-цель: BO-3 (Оптимизация фонда аудиторий и контроль нагрузки преподавателей)
- Источник: Учебное управление (Заказчик)
- Приоритет: Should

**Пользовательская история.** Как сотрудник Учебного управления, я хочу получать сводные отчеты по проценту занятости аудиторий и распределению часов преподавателей, чтобы оптимизировать использование помещений вуза и контролировать выполнение учебных планов.

**Сценарий UC-4.**

| Поле | Содержание |
| ----- | ----- |
| Акторы | Сотрудник Учебного управления. Микросервис расписания |
| Предусловия | В базе микросервиса сохранено актуальное расписание и справочники подразделений за нужный период |
| Триггер | Запрос пользователя на формирование сводки с выбранными фильтрами |
| Постусловие успеха | На экране построена сводная таблица с процентом занятости аудиторий, часами преподавателей и списком конфликтов BR-2 |
| Постусловие отказа | Отчет не построен; выведено предупреждение о нехватке данных за указанный интервал |

Основной поток:

1. Сотрудник Учебного управления указывает параметры: семестр, учебный корпус, кафедру или диапазон дат.
2. Микросервис собирает данные о запланированных занятиях из локальной базы данных.
3. Микросервис рассчитывает процент занятости каждой аудитории (отношение занятых пар к общему времени).
4. Микросервис считает часы нагрузки преподавателей и сравнивает их со ставкой из справочника.
5. Микросервис добавляет в отчет список найденных при импорте нарушений правила BR-2.
6. Система формирует итоговый отчет.

Альтернативы:

1. Экспорт сводки: пользователь нажимает кнопку выгрузки, и система формирует печатную форму или файл таблицы.

Исключения:

1. В базе данных нет записей расписания за выбранный период. Система останавливает расчет и предлагает изменить фильтры или сначала выполнить импорт данных (UC-1).

### 5.3. Однозначность и проверяемость

| Исходное требование | Проблема | Исправленное требование |
|---------------------|----------|-------------------------|
| «Мгновенно получать карточку с занятиями» в черновике US-3 / EP-8 | Слово «мгновенно» неизмеримо | Время ответа бота не больше 2 секунд (критерий SM-3 концепции) |
| «Наглядно просматривать сетку расписания» в черновике US-4 / EP-5 | Слово «наглядно» размыто | Сетка показывает дни недели и пары с 1 по 8 с фильтрами по группе, преподавателю и аудитории, загрузка до 2 секунд (SM-3) |
| «Обеспечить бесперебойную доступность расписания» в черновике EP-1 | Слово «бесперебойная» не задает метрику | При отказе сервера 1С база микросервиса отдает расписание без потери ранее сохраненных данных (NFR-A3) |
| «Своевременно корректировать планы» в черновике EP-6 | Слово «своевременно» неизмеримо | Пуш-уведомление приходит в течение 5 минут после обновления данных в 1С (Выпуск 2) |
| «Тяжелые и легкие справочники 1С» в черновике сценариев | Размытое деление | Заданы точные таймауты: 1800 секунд для подразделений и сотрудников (NFR-A1), 600 секунд для групп и планов (NFR-A2) |
| «Вовремя выявлять несогласованность данных» в EP-3 | Нет момента проверки | Проверка накладок запускается сразу при импорте до отправки в бот и Mini App |
| Не выявлено других размытых слов в EP-2, EP-4, EP-7 | Просмотрены эпики аудита, отчетов и Excel | Формулировки историй оставлены |

### 5.4. Непротиворечивость

| Требование A | Требование B | Конфликт | Решение |
|--------------|--------------|----------|---------|
| EP-1: расписание загружается из 1С | EP-3: при накладках фиксируется ошибка | Непонятно: если в 1С накладка, отменять ли весь импорт | Импорт не отменяется, иначе вуз останется без расписания. Спорные пары сохраняются, но помечаются как конфликт для отчета EP-4 |
| EP-1: расписание хранится в базе микросервиса | EP-5 и EP-8: пользователи смотрят расписание | Запросы из чата и Mini App могут перегрузить 1С | Пользователи читают данные только из базы микросервиса, прямых запросов к 1С от пользователей нет |
| EP-6: бот рассылает пуши при изменениях | Ограничения мессенджера MAX на спам | При массовом переносе пар отправка сотен сообщений разом приведет к бану бота | Сообщения отправляются пачками по 100-300 штук с паузой, а при сбое сохраняются в очередь (риск RI-3) |
| EP-5: расписание в Mini App | EP-8: расписание в чат-боте | Данные в боте и в Mini App могут не совпадать | Mini App не имеет отдельной базы, а берет данные у того же микросервиса бота. Данные всегда одинаковые |
| EP-7: выгрузка расписания в Excel | EP-2: журнал аудита | Диспетчер может выгрузить файл и изменить его без ведома системы | Каждая выгрузка в Excel записывается в журнал аудита с именем сотрудника и временем |
